# Library Management System

A console-based library management system written in **C#**.

This project is intended as a continuation of the `expense_tracker` mini-project. The goal is to practice object-oriented programming with multiple classes that interact with each other.

The main challenge in this project is managing relationships between objects, such as members borrowing and returning books.

---

## Project Goals

The project should help practice:

- Classes and objects
- Constructors
- Properties
- Lists
- Enums
- Methods
- Input validation
- Searching collections
- Object relationships
- Separation of responsibilities
- Encapsulation
- Refactoring

The project should be implemented using basic C# and .NET without relying on advanced frameworks.

---

## Main Features

When the program starts, the user should be able to choose between commands similar to:

```text
=== Library Management System ===

1. Add book
2. Add member
3. Show all books
4. Show all members
5. Borrow book
6. Return book
7. Search for book
0. Exit
```

The exact command names and structure may be changed during development.

---

## Requirements

### 1. Add a Book

The user should be able to add a new book to the library.

A book should contain at least:

- Title
- Author
- ISBN
- Availability status

Example:

```text
Title: The Hobbit
Author: J.R.R. Tolkien
ISBN: 9780261103344
```

The book should be stored in the library after being created.

#### Consider

- Should two books be allowed to have the same ISBN?
- What should happen if required input is empty?

---

### 2. Add a Member

The user should be able to register a new library member.

A member should contain at least:

- ID
- Name

Example:

```text
Member ID: 1001
Name: Alice
```

Each member should have a unique ID.

#### Consider

- Should the ID be entered by the user or generated by the program?
- What happens if a duplicate ID is entered?

---

### 3. Show All Books

The program should display all books currently stored in the library.

Example:

```text
Books:

The Hobbit
Author: J.R.R. Tolkien
ISBN: 9780261103344
Status: Available

1984
Author: George Orwell
ISBN: 9780451524935
Status: Borrowed
```

The program should handle an empty book collection without crashing.

---

### 4. Show All Members

The program should display all registered members.

Example:

```text
Members:

ID: 1001
Name: Alice

ID: 1002
Name: Bob
```

The program should handle an empty member collection.

---

### 5. Borrow a Book

A registered member should be able to borrow an available book.

The program should ask for information that identifies:

- The member
- The book

For example:

```text
Member ID: 1001
Book ISBN: 9780261103344
```

A book should only be borrowed if:

- The member exists
- The book exists
- The book is currently available

After the book has been borrowed, its state should change so that another member cannot borrow it at the same time.

#### Consider

- Where should the `BorrowBook()` method belong?
- Should the `Book` know which member has borrowed it?
- Should the `Member` contain a list of borrowed books?
- Should the `Library` class manage the relationship?

Choose a design and be prepared to explain why.

---

### 6. Return a Book

A member should be able to return a book they previously borrowed.

The program should verify that:

- The member exists
- The book exists
- The book is currently borrowed
- The member returning the book is allowed to return it

After the return, the book should become available again.

---

### 7. Search for a Book

The user should be able to search for books.

At minimum, support searching by title.

Example:

```text
Search: hobbit
```

Possible result:

```text
The Hobbit
Author: J.R.R. Tolkien
ISBN: 9780261103344
Status: Available
```

The search should preferably ignore differences in capitalization.

For example:

```text
hobbit
Hobbit
HOBBIT
```

should be treated as equivalent searches.

#### Optional

Support searching by:

- Author
- ISBN

---

### 8. Input Validation

The program should handle invalid input without crashing.

Examples include:

```text
Member ID: banana
```

or:

```text
ISBN:
```

or attempting to borrow a book that does not exist.

The user should receive a useful message explaining the problem.

## Minimum Class Requirements

The project should contain at least the following classes.

### `Book`

Represents one book.

Possible properties:

```text
Title
Author
ISBN
IsAvailable
```

Do not assume these are necessarily the final properties. Adjust the design if needed.

---

### `Member`

Represents one library member.

Possible properties:

```text
Id
Name
```

You may need additional properties depending on how borrowing is implemented.

---

### `Library`

Represents the library and manages the collections of books and members.

It will likely contain:

```text
List<Book>
List<Member>
```

Possible responsibilities include:

```text
AddBook
AddMember
FindBook
FindMember
BorrowBook
ReturnBook
```

You should decide which responsibilities belong here instead of copying this structure directly.

---

## Architecture Goal

Try to keep `Program.cs` focused mainly on user interaction.

A possible separation of responsibilities could look like:

```text
Program.cs
├── Read commands
├── Read user input
├── Print output
└── Call methods on other classes

Library
├── Store books
├── Store members
├── Search
├── Borrow books
└── Return books

Book
├── Book data
└── Book state

Member
├── Member data
└── Possibly borrowed books
```

The exact architecture is part of the exercise.

Before implementing everything, decide which class should be responsible for each operation.

## Development Stages

Build the project incrementally.

### Stage 1 — Basic Objects

Implement:

- `Book`
- `Member`
- `Library`

Add some test data and verify that objects can be created and stored.

---

### Stage 2 — Basic Commands

Implement:

- Add book
- Add member
- Show books
- Show members
- Exit

Get these features working before implementing borrowing.

---

### Stage 3 — Borrowing

Implement:

- Find member
- Find book
- Borrow book
- Prevent borrowing unavailable books

This is one of the main challenges of the project.

---

### Stage 4 — Returning

Implement:

- Return borrowed books
- Make returned books available again
- Prevent invalid returns

---

### Stage 5 — Search and Validation

Implement:

- Search by title
- Case-insensitive searching
- Duplicate checks
- Input validation
- Useful error messages

---

### Stage 6 — Refactoring

After the program works, review the structure.

Look for:

- Methods that are too long
- Repeated code
- Public collections that should be private
- Classes with too many responsibilities
- Logic in `Program.cs` that belongs elsewhere
- Unused variables or methods
- Inconsistent naming

The goal is not only to make the application work, but to improve the design after seeing how the different parts interact.

---

## Constraints

For the first version:

- Use a console application
- Use standard C# and .NET
- Use `List<T>` for collections
- Avoid databases
- Avoid external packages
- Avoid LINQ when a normal loop would provide useful practice
- Do not focus on file persistence yet

The purpose is to practice core programming and object-oriented design.

---

## Optional Extensions

Only consider these after the required version is complete:

- Limit how many books a member can borrow
- Add due dates
- Add overdue-book checking
- Add book genres
- Show all books borrowed by a member
- Show who currently borrowed a book
- Remove books
- Remove members
- Edit books
- Edit members

- Save and load data from files

These are optional and should not distract from completing the core project first.

---

## Completion Criteria

The project can be considered complete when:

- Books can be added
- Members can be added
- Books and members can be displayed
- Members can borrow available books
- Borrowed books cannot be borrowed again
- Members can return books
- Books can be searched
- Invalid input is handled
- Duplicate identifiers are handled
- Responsibilities are reasonably separated between classes
- `Program.cs` is not responsible for directly managing the internal collections
